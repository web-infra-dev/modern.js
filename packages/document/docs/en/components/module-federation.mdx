Module Federation (MF) is a technology solution that allows multiple JavaScript applications to share code and resources. Similar to microservices architecture on the server side, it allows you to split large applications into multiple independent smaller applications that can be developed, tested, and deployed independently, while dynamically loading modules from other applications at runtime.

Module Federation solves the problem of code duplication across multiple frontend applications. In the traditional approach, if multiple applications need to use the same components or utility functions, you would need to duplicate this code in each application, leading to code duplication, high maintenance costs, and larger application sizes. With Module Federation, you can place common code in one application and have other applications load it dynamically as needed, enabling code sharing and reducing duplication.

Module Federation 2.0 supports [Rspack](https://rspack.rs/) build tools, and provides enhanced features such as dynamic type hints, Manifest, Federation Runtime, runtime plugin system, and Chrome Devtools support for better development experience and debugging capabilities. You can visit the [Module Federation official documentation](https://module-federation.io/) to learn more.

Modern.js provides an example project for Module Federation. Please refer to [module-federation-examples - modernjs](https://github.com/module-federation/module-federation-examples/tree/db5bdbeee56f779999a2c591fc553eb94eb20b36/modernjs).

## Built-in integration

Modern.js automatically enables Module Federation when `module-federation.config.ts` exists in the application directory. No Modern.js MF plugin installation or registration is required. Install the MF engine:

```bash
pnpm add @module-federation/enhanced@0.0.0-feat-bridge-route-navigation-20261030085657
```

Import unified React consumers from `@modern-js/runtime/mf`. Modern manages Bridge, while applications install an Enhanced version supporting these APIs and expose protocol metadata. Existing direct Bridge imports remain supported.

Keep the common MF configuration in its existing file:

{/* prettier-ignore */}
```ts title="module-federation.config.ts"
import { createModuleFederationConfig } from '@module-federation/enhanced'

export default createModuleFederationConfig({
  name: 'host',
  remotes: {
    remote: 'remote@http://localhost:3001/mf-manifest.json',
  },
})
```

Register `appTools()` in `modern.config.ts`. The built-in adapter integrates CSR/SSR builds, combined manifests, SSR data fetching, remote updates in development and server asset handling.

The adapter defaults the top-level `shareStrategy` to `'loaded-first'` for both browser and server builds. Set `shareStrategy` explicitly in `module-federation.config.ts` to override it. Shared entries inherit this default through the MF runtime, without an additional strategy runtime plugin.

### moduleFederation

| Value   | Behavior                                             |
| ------- | ---------------------------------------------------- |
| Omitted | Enable when the default MF configuration file exists |
| `false` | Disable built-in MF, allowing the legacy plugin      |
| `true`  | Read the default file and fail if it is missing      |
| Object  | Enable MF and configure its Modern.js adapter        |

{/* prettier-ignore */}
```ts title="modern.config.ts"
import { appTools, defineConfig } from '@modern-js/app-tools'

export default defineConfig({
  moduleFederation: {
    fetchServerQuery: { source: 'host' },
  },
  plugins: [appTools()],
})
```

The object accepts the existing adapter options:

| Option                       | Description                                                                                              |
| ---------------------------- | -------------------------------------------------------------------------------------------------------- |
| `config`                     | Inline MF configuration, taking priority over the file                                                   |
| `configPath`                 | Custom MF configuration path, relative to the application directory                                      |
| `ssr`                        | Enable MF SSR, following `server.ssr` by default, or provide `{ distOutputDir }`                         |
| `fetchServerQuery`           | Additional query parameters for client calls to server data functions                                    |
| `autoOptimization`           | Set client/server optimization targets automatically, enabled by default and preserving explicit targets |
| `secondarySharedTreeShaking` | Preserve the existing plugin switch, disabled by default                                                 |

`server.ssr` still controls SSR for the Modern application. Keep common options such as `exposes`, `shared`, `runtimePlugins`, `dts` and manifests in the MF configuration file.

### Migrating from the legacy plugin

Remove the registration and dependency for `@module-federation/modern-js-v3`, then install `@module-federation/enhanced`. Import configuration helpers from enhanced and runtime APIs from `@module-federation/enhanced/runtime`.

Existing integrations may continue importing React Bridge APIs from `@module-federation/bridge-react`. Use `/v18` and `/v19` for version-specific entries, `/data-fetch` for data APIs and `/plugin` for the runtime plugin. When importing those APIs directly, install bridge-react at the same preview version as enhanced. No direct runtime or runtime-core application dependencies are needed.

For gradual migration, keep the legacy plugin and explicitly set `moduleFederation: false`. A project with an MF configuration file otherwise enables the built-in adapter automatically. Enabling both integrations fails with a migration message, including legacy registration through another plugin's `usePlugins`.

### Unified React consumers

{/* prettier-ignore */}
```tsx
import { createReactRemote, ReactRemote } from '@modern-js/runtime/mf'

const Card = createReactRemote<{ label: string }>({
  remote: 'remote/Card',
  loading: <span>Loading</span>,
  fallback: ({ error, retry }) => <button onClick={retry}>{error.message}</button>,
})

<Card label="Example" />
<ReactRemote remote="remote/Card" props={{ label: 'Example' }} />
```

`remote` accepts three input forms: a registered `alias/Expose` string, a function calling MF `loadRemote`, or a function returning a preloaded MF namespace or component export. Functions can return synchronously or asynchronously. Factory and declarative consumers use the same behavior.

{/* prettier-ignore */}
```tsx
import { loadRemote } from '@module-federation/enhanced/runtime'
import Shop, * as ShopModule from 'shop/Card'
import { createReactRemote, ReactRemote } from '@modern-js/runtime/mf'

const ById = createReactRemote({ remote: 'shop/Card' })
const ByLoader = createReactRemote({
  remote: () => loadRemote('shop/Card'),
})
const loadShop = () => ShopModule
const ByModule = createReactRemote({ remote: loadShop })
const ByComponent = createReactRemote({ remote: async () => Shop })

<ReactRemote remote={loadShop} props={{ label: 'Example' }} />
```

Always wrap function inputs in a thunk, such as `remote: () => Shop`. The returned value must come from MF loading or a static remote import. The consumer uses its existing source information to identify the component or Bridge protocol. Users do not add module markers. Passing a component function or namespace object directly is not one of these input forms. Preloaded component provenance is supplied by the matching consumer Runtime version, without rebuilding producers or adding producer markers.

Keep function inputs to `ReactRemote` stable across renders by defining them at module scope, as above, or using `useCallback`. Reuse the same function when only business props change. Replacing the function reference selects a new loading source and resets that consumer instance's loading and component state.

Preloaded values must come from the same Runtime instance used by the consumer. A component reference shared by multiple exposes or versions is ambiguous, so use a remote ID string to select its source. Older runtimes retain compatibility through MF-identified namespaces, while preloaded default exports require the matching newer Runtime.

With MF-generated type mappings included in the consumer project, literal remote IDs infer expose props. Function inputs infer props from the returned namespace or component, and `exportName` accepts its renderable exports. Both factories and `ReactRemote` share these checks. Dynamic strings or remotes without declarations can retain an explicit props type, such as `createReactRemote<{ label: string }>(...)`.

The consumer selects an adapter from the manifest expose protocol. Ordinary React
components render in the Host tree with the existing SSR, hydration and data-loading
integration. Default provider exports created with `createBridgeComponent` publish
`render: 'bridge'` and `isService: false`, and mount in independent client Roots.
Each mounted instance owns its provider, reuses its Root for props updates and
releases it on unmount.

Producers keep standard exposes. The build analyzer follows imported factory
bindings, aliases and static re-exports without executing producer code. Default
provider exports must be statically analyzable. Ambiguous wrappers, dynamic options
and conflicting protocol metadata produce build diagnostics.

`exportName` defaults to `default` and supports ordinary named component exports.
Unmarked legacy components retain the component path. Legacy Bridge providers can
set `render: 'bridge'` explicitly. Hints conflicting with reliable metadata fail.
General registration and loading APIs remain in `@module-federation/enhanced/runtime`.

All three forms support ordinary component SSR when the function and loaded modules can execute in Node. Components use the same data-loading, asset and hydration pipeline. With `noSSR: true`, the server emits the loading placeholder and the consumer calls the function and renders the component on the client. Static imports and preloading performed outside the consumer are not undone by `noSSR`.

Bridge only emits a placeholder on the server in this API version. The client creates its provider and independent Root. A function input may load the module to identify its protocol on the server, but does not render the Bridge application. A string input can select Bridge from metadata before loading the expose. Bridge SSR, Service App execution and `updateRemotes` remain separate capabilities. Retry invokes a failed input function again and resets the failed instance, without promising to download an already cached MF module or replay business data loaders.

Modern disables dependency-based automatic Bridge router aliases by default because it manages routing itself. Explicit bridge.enableBridgeRouter configuration is preserved.

## Export a Modern route scope

Use `createRoot({ route })` in a dedicated expose module and pass the returned ModernRoot to `createBridgeComponent`:

{/* prettier-ignore */}
```tsx title="src/export-product.tsx"
import '@modern-js/runtime/registry/index'
import { createRoot } from '@modern-js/runtime/react'
import { render } from '@modern-js/runtime/browser'
import { createBridgeComponent } from '@modern-js/runtime/mf'

const ModernRoot = createRoot({ route: '/product' })

export default createBridgeComponent({
  rootComponent: ModernRoot,
  render: (Component, dom) => render(Component, dom),
})
```

Add this module to the MF `exposes` configuration. Import the registry explicitly. Multiple entries use their own registry, such as `@modern-js/runtime/registry/admin`.

`route` selects a fixed producer route definition. The build retains all descendants, ancestor layouts, loaders, error boundaries, and necessary index and pathless wrappers. Unrelated sibling branches are removed before generating page imports. The selector only chooses the exported content. The build generates application-local routes for this export while preserving route IDs and the producer's standalone route table. The selected source path does not become an application basename. Consumers mount the selected content as an application, using the same mounting contract as a complete application export. The Modern route consumer below can infer the mount basename and synchronize navigation.

Omitting `route`, including calling `createRoot()`, exports the registry's complete application. The existing `createRoot(UserApp)` component overload remains supported. Each export has its own route definition and each mount owns a separate Router and runtime context. Exported applications use Browser Router by default and retain the producer runtime configuration for Hash Router. Selecting a route does not enable Memory Router. Browser instances share the window URL and history. Props updates preserve page state, and remounting creates a fresh instance.

The selected expose does not import unrelated pages through its route configuration. Those pages may still appear in dist when another entry, expose, or business import needs them.

For this version, keep the registry import, `createRoot` call and default `createBridgeComponent` provider in the same expose definition module, with one application Root per module. Imported aliases, literals and resolvable local constants are supported. Missing paths, dynamic or wildcard selectors, independent same-path branches and non-static options produce build errors. Dynamic children inside a fixed scope remain supported.

Explicit scopes use the build-time route graph. They cannot replace it with `runtime.router.createRoutes`, and runtime route hooks cannot change the selected topology. RSC scope exports are not supported yet.

Server loaders continue using Modern data endpoints at the producer asset origin, preserving the entry base and original route paths. Deploy the matching data endpoints at that origin and configure cross-origin access explicitly, or provide a same-origin proxy. A static-only CDN does not automatically provide a loader service. Bridge still emits a placeholder on the Host server, and this feature does not enable Bridge SSR.

## Mounting on Modern routes

Use `createModernReactRemote` in the wildcard route that owns the remote application's URL:

{/* prettier-ignore */}
```tsx title="src/routes/stores/[storeId]/inventory/$.tsx"
import { createModernReactRemote } from '@modern-js/runtime/mf'

export default createModernReactRemote({ remote: 'shop/Product' })
```

The component reads its local route match at render time, computes the mount basename, and connects host and remote navigation. With Host Router basename `/admin`, the URL `/admin/stores/100/inventory/detail/42?tab=stock#summary` has mount prefix `/admin/stores/100/inventory`. Dynamic parameters use their matched values. Pathless layouts and index routes add no segments. The wildcard tail is excluded. Configure the host wildcard route explicitly.

`useRemoteBasename()` exposes the same calculation. An explicit basename overrides inference and includes the Host Router basename:

{/* prettier-ignore */}
```tsx
import { ReactRemote, useRemoteBasename } from '@modern-js/runtime/mf'

export default function Page() {
  const basename = useRemoteBasename()
  return <ReactRemote remote="shop/Product" basename={basename} />
}
```

Generic `createReactRemote` and `ReactRemote` imported from `@modern-js/runtime/mf` do not infer a mount basename merely because they appear inside a route. Omitting basename does not enable independent navigation. For dashboard cards, explicitly pass `memoryRoute: { entryPath: '/' }`. Only this option enables an independent Memory Router, with local entry paths and no Host URL synchronization. The mode and entry path are chosen at mount time. Remount to change the mode or reset the entry path. Keep business props separate from basename, navigation, and memoryRoute controls. The basename stays fixed for one mount. Ordinary props updates and internal navigation reuse the Root and preserve page state. Changing the actual mount basename disposes the old mount and creates a new instance, without preserving the Router or page state across mount locations. Unmount releases that instance's subscriptions and loader requests. Retry creates a fresh instance.

### Producer routing responsibility

`createRoot({ route: '/product' })` only chooses the exported application content. The consumer owns its mount path. The selector does not set a producer basename or change the producer application's standalone routing.

For an application selected from `/product`, the local detail route and `useLocation().pathname` are `/detail/42`. When mounted at `/inventory`, the browser detail URL is `/inventory/detail/42`. Navigation only adds or removes the consumer basename and never restores `/product`. Consumers do not pass the selection path, and manifests or Snapshots need no new path metadata. Ancestor layouts, loaders, and page state remain available.

The standalone producer still uses `/product/detail/42`. Server loaders continue to request the original producer data endpoints, independently of application navigation. An independent memory application also uses local paths for `memoryRoute.entryPath`, such as `/detail/42?tab=stock`. The framework does not rewrite business source code.

A persistent export also observes Host locations outside its mount. React Router cancels its previous pending navigation before handling the new location, so a late loader cannot navigate the Host back. An initial loader redirect also notifies the Host before page content finishes loading, without writing history again. Browser hosts with an explicit basename receive this notification without an additional navigation adapter. Repeated notifications for the same history entry do not restart pending loaders. A new history entry at the same URL still counts as a new navigation. Mount-prefix matching follows React Router's case-insensitive basename semantics and preserves encoded route segments.

Prefer relative Link, navigate, and redirect targets in portable producers. Producers also own compatibility for code depending on basename or pathname. Relative navigation generates URLs but does not change the route graph. Hard-coded absolute paths are not scanned or rewritten. Unmatched paths follow normal route error handling.

### Other routers and compatibility

Without Modern Router, pass basename explicitly to `createReactRemote` or `ReactRemote`. The remote Browser Router writes history once for push or replace and publishes popstate to notify the Host Router and other browser instances. Host notifications update the remote location without another history write. The Host chooses the mount location and passes the actual basename at initial mount. The Remote owns its Router, internal paths and business navigation. Changing basename remounts the application and disposes the old Router, pending loaders and subscriptions. A custom Router that changes history with pushState without publishing location changes needs a `navigation` adapter with `getLocation`, `subscribe`, and `navigate`. A pathname string alone cannot subscribe to arbitrary Routers.

History entry keys distinguish a new navigation at the same URL from an old notification. Custom browser Routers should generate a new `history.state.key` on push or replace and retain entry keys during back and forward navigation. Calling `pushState(null, '', sameURL)` and publishing only the same pathname cannot distinguish a new navigation from a delayed notification.

URL-connected Host and Remote must use the same Browser or Hash Router mode. A CSR Hash Router host requires a producer configured with `router.supportHtml5History: false` for URL-connected application mounts. A default Browser Router remote does not interpret the Host hash as its pathname. Use an explicit `memoryRoute` for an independent card instead. Hash hrefs are never concatenated as pathnames. Custom Modern documents may include a `<base>` element. Hash Router can then generate complete href URLs, and synchronization still uses the configured Hash mode. Custom adapters that do not write browser history are outside this Browser Router synchronization contract. Fragments are absent from server requests, so hash entry locations are resolved in the browser. SSR hydration of Hash Router hosts is not supported in this version.

Legacy Bridge providers retain their existing Router behavior. Providers without navigation integration do not gain automatic synchronization. Unmarked providers still need `render: 'bridge'`. Ordinary components remain in the host React tree. Bridge produces a placeholder in SSR hosts and connects navigation after client mounting. Bridge SSR, Service App execution, and remote version replacement are outside this feature.
