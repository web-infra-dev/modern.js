# MCP Apps

Modern.js builds React cards for MCP hosts. UI builds and servers exchange only `ui-manifest.json`. Servers use the official MCP SDK directly.

## Create a project

```bash
npx @modern-js/create@latest my-mcp --template mcp-apps
npx @modern-js/create@latest my-mf-mcp --template mcp-apps --mf
npx @modern-js/create@latest my-server --template mcp-server
```

Choose a release containing MCP Apps support. Run `pnpm dev`. The explicit BFF route is `/api/mcp`.

The application must install the peers `@modelcontextprotocol/server` and `@modelcontextprotocol/ext-apps` so tools, resources and HTTP handling use the application's SDK versions. `@modern-js/server-runtime` is an optional peer, loaded only when invoking a BFF handler. Standalone Fetch servers do not require it. The project templates already declare these dependencies.

## Build cards

Declare local default-export React components or this project's MF exposes in `mcp-views.json`:

```json
{
  "views": {
    "todos": "./src/components/Todos.tsx",
    "stats": { "expose": "./Stats" }
  },
  "csp": { "resourceDomains": [], "connectDomains": [] },
  "prefersBorder": true
}
```

Add `mcpAppsPlugin({ views: './mcp-views.json' })` to your Modern.js plugins. Paths resolve relative to the JSON file. MF cards require the Modern.js MF plugin with manifest output enabled. The UI plugin validates exposes against the actual emitted MF manifest and builds the shell with the application's React dependencies.

{/* prettier-ignore */}
```tsx
import type { McpViewProps } from '@modern-js/mcp-apps/react'

export default function Todos({
  todos = [],
  mcpApp,
}: McpViewProps<{ todos: string[] }>) {
  return (
    <section>
      <ul>
        {todos.map(todo => (
          <li key={todo}>{todo}</li>
        ))}
      </ul>
      <button
        onClick={() =>
          mcpApp.callServerTool({ name: 'refresh', arguments: {} })
        }
      >
        Refresh
      </button>
    </section>
  )
}
```

Props come from successful `structuredContent`. The reserved `mcpApp` prop is injected by the wrapper. Input arguments are not merged into props. New input, cancellation and teardown clear previous output. The wrapper manages connection, host styling and loading/error states. Results from tools called inside a card must be handled by the component itself.

## Write the server

Enable `bffPlugin()` and create `api/lambda/mcp.ts`. The UI plugin does not register any HTTP route.

{/* prettier-ignore */}
```ts
import { McpServer } from '@modelcontextprotocol/server'
import { registerAppTool } from '@modelcontextprotocol/ext-apps/server'
import {
  createBffHandlers,
  registerUiResources,
} from '@modern-js/mcp-apps/server'
import { z } from 'zod'

async function createServer(request: Request) {
  const server = new McpServer({ name: 'todos', version: '1.0.0' })
  const ui = await registerUiResources(server, { request })
  registerAppTool(
    server,
    'list_todos',
    {
      inputSchema: z.object({}),
      _meta: { ui: { resourceUri: ui.todos } },
    },
    async () => ({
      content: [{ type: 'text', text: 'Todo list' }],
      structuredContent: { todos: ['Read the MCP Apps guide'] },
    }),
  )
  return server
}

export const { POST, GET, DELETE } = createBffHandlers(createServer)
```

The adapter reconstructs BFF's consumed JSON body and returns the SDK Response. The official SDK owns protocol serving and tool validation. Serving is stateless, so unsupported session operations such as GET and DELETE are rejected by the SDK. Return a fresh server per request. Put authentication and authorization in surrounding middleware or the factory, and persist business data in an external store.

For independent Hono servers, create `handle = createFetchHandler(createServer)` and mount `app.all('/mcp', c => handle(c.req.raw))`. Foreign browser origins are rejected unless listed in `allowedOrigins` in the adapter's second argument.

## Manifest and deployment

Builds emit `dist/mcp-apps/ui-manifest.json` and `dist/mcp-apps/ui/*.html`. Static JavaScript, CSS and MF files remain in the application's standard output. MF-only projects also emit a UI manifest. Local HTML filenames use a stable hash of the view name. MF cards share `mcp-shell.html`.

The version 1 manifest contains `assetBase`, `remotes` and `views`. A local view has `{ html, ui }`. An MF view has `{ remote, expose, ui }`, with its remote declaring `{ entry, shell }`.

- HTML and shell paths resolve relative to the manifest location
- MF entry paths resolve relative to `assetBase`
- Absolute HTTP(S) sources are supported for independent deployments
- `ui` preserves CSP, permissions, domain and border preferences
- Resource URIs are generated as `ui://app/<encoded-view-name>` by the server, and multiple tools can share a card
- MF configuration is injected into resource HTML instead of tool results

`registerUiResources()` loads the manifest asynchronously. Defaults are `dist/mcp-apps/ui-manifest.json` in production and `node_modules/.modern-js/mcp-apps/ui-manifest.json` in development. Set its `manifest` option to a file path or HTTP(S) URL for custom output directories or independent servers. Relative HTML resolves against that location.

Manifests are cached by source URL and environment. Production caches successful loads for the process lifetime, so updating the same location requires a process restart. Development detects local file changes and caches remote manifests for 60 seconds. Concurrent loads are coalesced and failures can be retried. HTML is read per resource request, and request-specific URLs and metadata remain isolated.

An absolute `output.assetPrefix` becomes `assetBase`. Otherwise request-origin resolution is used. Override `assetBase` in `registerUiResources` for a separate static origin or deployment path prefix. Request mode honors sanitized `x-forwarded-proto` headers. Reverse proxies must preserve the public host and sanitize forwarded headers.

Required asset, connection and base URI origins are added to CSP. MF entry origins are also added to connection permissions. Declare any additional API, chunk/CDN or iframe origins explicitly. Deploy the manifest and HTML together with the application static assets and MF output.

Platforms may rewrite file and MF addresses to absolute URLs and combine cards into another manifest of the same version. Unknown versions are rejected.

## Card capabilities

Cards advertise `inline` and `fullscreen` by default. Both local component modules and MF exposes can export `mcpCapabilities` to declare additional capabilities or override the display modes.

{/* prettier-ignore */}
```tsx
import type { McpCapabilities } from '@modern-js/mcp-apps/react'

export const mcpCapabilities = {
  availableDisplayModes: ['inline'],
} satisfies McpCapabilities

export default function Card() {
  return <div>My card</div>
}
```

You can also pass capabilities as the third argument to `createMcpView`. Explicit display mode arrays replace the defaults. MF modules are loaded before initialization so the handshake includes their capabilities. Declaring fullscreen support does not add a fullscreen button or switch modes automatically.

## Debug with the official MCP Inspector

Start the application with `pnpm dev`. In a second terminal, run `pnpm inspect` in a generated MCP project. The command launches the official Inspector as a separate development process with the Streamable HTTP endpoint preconfigured. Existing projects can run:

```bash
npx --yes @modelcontextprotocol/inspector@2.12.0 --transport http --server-url http://localhost:8080/api/mcp
```

Open the address printed by the Inspector and connect the server. Override the address with `pnpm inspect --server-url http://localhost:9090/api/mcp` when using a custom port. Inspector 2.12.0 requires Node.js 22.19.0 or newer. It is downloaded on demand and is not a production dependency or an embedded framework page.

Inspector 2.12.0 includes an Apps page that discovers tools linked to UI resources and renders their cards. Use it to test local and MF views, then inspect Tools, Resources and protocol logs for debugging.
