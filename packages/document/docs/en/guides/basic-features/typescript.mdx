# TypeScript Configuration

Modern.js ships shared TypeScript presets in `@modern-js/tsconfig`. A project usually needs just two files: the main `tsconfig.json`, and a `tsconfig.server.json` only when it has server-side code.

## Presets

| Preset | Purpose |
| --- | --- |
| `@modern-js/tsconfig/base` | Main config. `module: ESNext`, `moduleResolution: bundler`, `jsx: react-jsx`, `target: ES2022`, `strict`, `isolatedModules`. Used by the editor, Rspack alias resolution and type-checking. |
| `@modern-js/tsconfig/server` | Reference preset with the four server-side emit overrides: `module: NodeNext`, `moduleResolution: NodeNext`, `noEmit: false`, `declaration: false`. For tools that support `extends` arrays (tsc >= 5.0); the recommended `tsconfig.server.json` inlines the same fields. |
| `@modern-js/tsconfig/legacy` | The previous `base` (`module: commonjs`, `moduleResolution: node`, `target: ES2015`). Rollback aid only; TypeScript 6 reports these options as deprecated. |
| `@modern-js/tsconfig/react` | Deprecated alias of `base`. Use `base` directly. |

## Two-file layout

`tsconfig.json` is the single main config, and every path alias (`paths`) lives here:

```json title="tsconfig.json"
{
  "extends": "@modern-js/tsconfig/base",
  "compilerOptions": {
    "noEmit": true,
    "types": ["node"],
    "paths": {
      "@/*": ["./src/*"],
      "@shared/*": ["./shared/*"]
    }
  },
  "include": ["src", "shared", "config", "modern.config.ts"]
}
```

When the project has a BFF (`api/`) or a custom server (`server/`), add `"@api/*": ["./api/lambda/*"]` to `paths`, add `api` and `server` to `include`, and create:

```json title="tsconfig.server.json"
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "noEmit": false,
    "declaration": false
  },
  "include": ["api", "server", "shared"]
}
```

The framework uses this file to compile `api/`, `server/` and `shared/`, and for ts-node at dev time. The four `compilerOptions` override only their own keys; everything else, including `paths`, is inherited from `tsconfig.json`. They are the same fields as `@modern-js/tsconfig/server`, inlined because ts-node 10 does not support `extends` arrays.

## Why two files

Bundlers expect `module: ESNext`, while Node-side output has to match `package.json#type`: a project without `"type": "module"` needs CommonJS output. No single `module` value satisfies both, so the server side overrides the module options separately.

## Without `tsconfig.server.json`

The server config is resolved as `server.tsconfigPath` → `tsconfig.server.json` → `tsconfig.json`. Only when the framework falls back to `tsconfig.json`, its `module` is an ES module value, and the project is not `type: module`, server code is compiled with `module: NodeNext` + `moduleResolution: NodeNext` and a one-time warning is printed. `type: module` projects are never rewritten. See [server.tsconfigPath](/configure/app/server/tsconfig-path) for the full rule.

## Migrating an existing project

The previous create template wrote `"baseUrl": "./"` into `tsconfig.json`, and TypeScript 6 reports TS5101 for any `baseUrl` (the option is deprecated). Modern.js 3 no longer has a `modern upgrade` command; existing projects migrate with the `modernjs-migrate-to-v3` Skill. Its `migrate.mjs` performs the tsconfig changes below (projects already on v3 are handled as a continuation), and the tsconfig step can also be run on its own:

```bash
# Install the Skill (--agent: claude-code / codex / cursor / ...)
npx skills add web-infra-dev/modern.js --skill modernjs-migrate-to-v3

# Migrate only the tsconfig; <skillDir> is where the Skill was installed
node <skillDir>/scripts/migrate-tsconfig.mjs <projectDir>
```

Results go to `changed` (applied) and `manual` (left to you) in `<projectDir>/.agents/runs/modernjs-migrate/report.json`. The script is safe to run again.

| Project state | What the script does |
| --- | --- |
| `baseUrl` is `"./"` or `"."` and `paths` exists | Removes `baseUrl`; `paths` is unchanged |
| `baseUrl` is `"./"` or `"."` without `paths` | Keeps it and adds a manual item: bare imports resolved through `baseUrl` (such as `import 'src/foo'`) must first be mapped with `paths` (for example `"*": ["./*"]`), then `baseUrl` can be removed |
| `baseUrl` has any other value (such as `"./src"`) | Keeps it and adds a manual item with the rewritten `paths` |
| `api/lambda` exists and `paths` has no `@api/*` | Adds `"@api/*": ["./api/lambda/*"]`; if `baseUrl` is kept, this becomes a manual item for after the `baseUrl` rewrite |
| Not `type: module`, has `api/` or `server/`, no `tsconfig.server.json` and no `server.tsconfigPath` | Writes the `tsconfig.server.json` shown above |
| `tsconfig.json` contains comments or trailing commas | Leaves the file untouched and lists the edits above as manual items |

With any other `baseUrl`, each `paths` entry used to resolve against `baseUrl`. Before removing it, prefix every entry with the old `baseUrl` so it is relative to the directory of `tsconfig.json`:

```json title="Before"
{
  "compilerOptions": {
    "baseUrl": "./src",
    "paths": {
      "@/*": ["*"],
      "@shared/*": ["../shared/*"]
    }
  }
}
```

```json title="After"
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"],
      "@shared/*": ["./shared/*"]
    }
  }
}
```

Without the Skill, apply the same changes by hand.

## Notes

- Never declare `paths` in `tsconfig.server.json`: TypeScript replaces `paths` wholesale instead of merging it key by key.
- `baseUrl` is no longer needed. Relative entries in `paths` are resolved against the directory of the file that declares them.
- `@modern-js/tsconfig` 3.10 and later requires `@modern-js/app-tools` 3.10 or later.
