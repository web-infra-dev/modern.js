# Application SSR with built-in Module Federation

Built-in Module Federation renders Modern applications through the shared Bridge implementation. The browser reuses the server DOM and restores router and loader data. Enable `server.ssr: { mode: 'stream' }` in both applications and use matching MF packages that provide Bridge SSR support.

To recover through Modern's fallback request after an SSR failure, configure the consumer with `server.ssr: { mode: 'stream', forceCSR: true }`. `forceCSR` permits an explicit fallback request and does not disable normal SSR.

## Export an application

Configure the following producer module in MF `exposes`:

```tsx title="src/exports/ProductApp.tsx"
import '@modern-js/runtime/registry';
import { createRoot } from '@modern-js/runtime/react';
import { createModernBridgeComponent } from '@modern-js/runtime/mf';

const Root = createRoot({ route: '/product' });
export default createModernBridgeComponent({ rootComponent: Root });
```

Omit `route` to export the whole application. The option selects content, not a consumer URL prefix. Use portable relative links in producer code. Subsequent loader requests use the producer's data endpoint configuration.

The generic Bridge provider also accepts Modern's explicit callbacks:

```tsx
import {
  createBridgeComponent,
  render,
  hydrate,
  renderStream,
} from '@modern-js/runtime/mf';

export default createBridgeComponent({
  rootComponent: Root,
  render,
  hydrate,
  renderStream,
});
```

These callbacks render applications generated by `createRoot` and its registry. Existing CSR Bridge providers can keep using `createBridgeComponent` without adding callbacks.

### Browser and Node artifacts

The same producer module is compiled separately for the browser and Node. The built-in MF plugin selects `@modern-js/runtime/mf/server` for Node builds and redirects explicit `@module-federation/bridge-react/v18` and `/v19` producer imports to `/server`. Core’s default and `/base` entries use the package exports `node` condition. Browser builds keep the browser entries, without application-level `.server.ts` aliases.

The browser entry implements `render`, `hydrate`, updates and unmounting. The Node entry implements `renderStream` and request streaming. Both reuse the application definition and pure render-tree construction without importing the other runtime’s implementation. All three callback names remain exported, with lightweight errors for calls in the wrong environment. Custom builders must select the corresponding entry for each target. Filename suffixes alone do not perform this isolation.

## Consume an application

`createReactRemote` and `ReactRemote` continue to consume ordinary components and Bridge applications:

{/* prettier-ignore */}
```tsx
import { createReactRemote } from '@modern-js/runtime/mf'
import { loadRemote } from '@module-federation/enhanced/runtime'

const Product = createReactRemote({
  remote: () => loadRemote('shop/ProductApp'),
  basename: '/inventory',
  loading: <p>Loading products</p>,
})
```

The detail URL is `/inventory/detail/42`. The selection prefix `/product` is not restored. Inside a Modern route, the framework adapter connects navigation in both directions. `createModernReactRemote` can infer the basename of the mounting route.

`remote` requires a function, such as `() => loadRemote('shop/ProductApp')` or `() => Shop`, where `Shop` is an MF export previously loaded by the same runtime instance. The renderer is selected after loading, and typed results preserve business prop inference. The Host reserves SSR work before the function completes, including delayed Bridge registration. Use `noSSR` to prevent the consumer from executing the loader and its module on the server. It does not undo static imports performed outside the consumer.

The response contains remote HTML and recovery data. Each browser instance hydrates when its container and data are ready and handles subsequent stream data independently. Props updates and internal navigation preserve the Root, Router and page state. The basename stays fixed during a mount, and changing it disposes the old instance and mounts a new one.

Modern application exports always use progressive hydration. They send an initial loader snapshot followed by deferred data updates, without computing a duplicate final snapshot. Ready regions can hydrate and respond to interactions before all deferred values settle. Ordinary Modern SSR without MF does not use this application recovery path.

After successful SSR, initial hydration reuses server loader data and does not rerun `.data.client`. Subsequent browser navigation executes client loaders according to existing Modern semantics. Use `noSSR` for a consumer that requires its loader to run in the browser on the initial visit, such as a client-side redirect.

## Language and route prefetching

Each application restores its initial SSR language from its own snapshot without reading the consumer's global SSR language. Applications still manage their own translations. See [Integrating Internationalization](/guides/topic-detail/module-federation/i18n) for explicit `i18nInstance` sharing and independent instances.

Application `Link` components default to `prefetch="none"`. In the browser, `prefetch="intent"` and `prefetch="render"` use the current producer's route assets and server loader capability. Data requests use the same producer address and path translation as navigation loaders, such as consumer `/inventory/detail/42` mapping to producer `/product/detail/42`. Route JavaScript is loaded by the producer's own build runtime. A `noSSR` mount can still prefetch supported server loaders. Client-only loaders do not generate server data prefetch requests.

## Boundaries

The browser retains Browser Router or the configured Hash mode. Only explicit `memoryRoute` enables independent memory navigation. Browser Router hydrates its first frame from the server request snapshot, then adopts the current browser URL and fragment after commit. Creation-time subscriptions and the same Router instance are preserved.

Hash Router selects pages from the fragment, which is absent from HTTP requests and cannot select the initial server route. Use `noSSR` for these pages. Existing Hash navigation is unchanged.

The initial Modern Bridge SSR validation baseline is **React and React DOM 19.3.1**. The producer's server and browser versions must match.

Unpatched React 18.3.1 is outside the initial SSR support boundary. Its Node `renderToPipeableStream` can emit NUL bytes and corrupt HTML when multibyte characters cross buffer boundaries, reproducible in development and production. See the upstream fix in [React #26228](https://github.com/facebook/react/pull/26228) and the later 18.3.1 report in [React #31134](https://github.com/facebook/react/issues/31134). This integration neither patches React nor strips NUL bytes, and adds no runtime version guard. Existing CSR support is unchanged.

`noSSR` keeps browser-only rendering and does not execute the remote loader on the server. RSC applications, Service App HTTP deployment and caching are outside this integration.

Verify both the remote HTML frames in the original response and DOM reuse during hydration. Visible content after browser execution alone does not demonstrate SSR.
