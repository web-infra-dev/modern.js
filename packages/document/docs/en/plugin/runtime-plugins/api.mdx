# Plugin API

Runtime plugins extend initialization, root components and cleanup in ordinary pages and Bridge exports. Register them through [`plugins`](/configure/app/runtime/plugins) in `src/modern.runtime.ts`.

## Plugin Structure and Order

Each plugin has a unique `name`. `pre` lists plugins that must execute before it, while `post` lists plugins that must execute after it. `setup` receives the plugin API and may return a Promise. The framework waits for dependency setup to complete before continuing.

{/* prettier-ignore */}
```tsx
import type { RuntimePlugin } from '@modern-js/runtime'

export const preferencesPlugin = (): RuntimePlugin => ({
  name: 'preferences',
  pre: ['@modern-js/runtime-plugin-request-context'],
  setup(api) {
    const controller = new AbortController()
    api.onDispose(() => controller.abort())

    api.onBeforeRender(async context => {
      const url = new URL('/api/preferences', context.requestContext.request.url)
      const response = await fetch(url, { signal: controller.signal })
      context.preferences = await response.json()
    })
  },
})
```

Setup runs separately for each mount or server request. Do not store the current language, Request or loader results in module variables. See [Life Cycle](./life-cycle) for ownership and the full execution sequence.

## Reading and Updating Data

### `api.getRuntimeConfig`

Returns the current runtime configuration. Treat it as read-only data. Do not mutate it to store request state. Configuration is not React state.

### `api.getRuntimeContext`

Returns the context owned by the current instance. It is the same object passed to `onBeforeRender`. Page data, Bridge snapshots and server Requests enter through their respective data sources. Built-in plugins consume the current instance fields rather than another application's SSR globals.

The built-in request context plugin prepares `requestContext` during `setup`, before application plugins execute. Initial application data and asset capabilities enter the context during instance creation. Router adds route matches and loader results during initialization.

The `ssr` field is ready before setup. It is true during server initialization. In the browser, it indicates that the current page or Bridge instance has server bootstrap data, rather than whether React hydration has completed. CSR without those data sets it to false.

### `api.updateRuntimeContext`

Deeply merges a patch into the current context. It does not bind the supplied object as the context or track later changes to that object.

{/* prettier-ignore */}
```ts
const patch = { feature: { enabled: true } }
api.updateRuntimeContext(patch)
// Submit another patch, or mutate the current context, for later changes
api.updateRuntimeContext({ feature: { enabled: false } })
```

The internal React Provider uses the current context. The public `RuntimeContext` exposes a stable view that hides framework fields, without maintaining a second data copy. Field mutations do not trigger React renders automatically. Use React state or a subscription for reactive updates.

### `api.getHooks`

Returns lifecycle and extension hooks for the current instance. The framework owns normal application initialization. Do not repeat initialization hooks during component updates.

Use a `registryHooks` factory to create fresh extension hooks for each instance. If `registryHooks` is a record of hooks created with the standard helpers, Modern clones their hook containers for each instance and preserves callbacks registered in the static definition. Arbitrary third-party custom hook closures cannot be copied automatically. Create those hooks inside the factory rather than returning a shared hook object.

## Lifecycle APIs

### `api.onBeforeRender`

Registers an initialization callback. The framework executes and awaits callbacks in plugin dependency order, then runs `wrapRoot`. Browser props updates and internal navigation do not repeat this phase.

Callbacks may mutate the current context. Thrown errors and rejected Promises stop initialization. Use the second argument, `interrupt`, to stop explicitly. The platform adapter handles the result without running later hooks or mounting the application.

{/* prettier-ignore */}
```ts
api.onBeforeRender((context, interrupt) => {
  if (context.requestContext.request.headers['x-maintenance'] === 'true') {
    return interrupt(new Response('Temporarily unavailable', { status: 503 }))
  }
})
```

### `api.wrapRoot`

Registers a root component wrapper. It runs once after successful initialization, and its resulting component remains stable for the lifetime of the instance. Forward props to the original App to preserve application behavior and state across updates and navigation.

{/* prettier-ignore */}
```tsx
import { RuntimeContext } from '@modern-js/runtime'
import { useContext } from 'react'

api.wrapRoot(App => {
  function PreferencesRoot(props) {
    const context = useContext(RuntimeContext)
    return (
      <PreferencesProvider value={context.preferences}>
        <App {...props} />
      </PreferencesProvider>
    )
  }
  return PreferencesRoot
})
```

Use the Router plugin's `api.modifyRoutes` hook to modify instance routes. Declare a dependency on the Router plugin instead of using a mutable module-level route table.

### `api.onDispose`

Registers synchronous cleanup for the current instance. Remove listeners, clear timers, cancel pending work and release resources created by the plugin. Cleanup runs once per instance in reverse registration order.

Unmount, request output completion, failed initialization and cancellation dispose the instance. Registering cleanup on an already disposed instance executes it immediately, so register cleanup as soon as asynchronous work acquires a resource. Asynchronous operations must respond to AbortSignal rather than only ignoring React updates after unmount.
