# SSR 缓存更新与本地开发刷新

内置 Module Federation 可以在 Modern 服务进程内更新已经消费的远端，协调 SSR 请求、生产者工作和应用缓存。普通 SSR 组件、Bridge SSR 与 Service App 使用同一套更新入口。生产环境由业务发布流程主动调用，开发环境订阅生产者变化，并在无法订阅时通过请求前检查发现更新。

:::warning 当前构建要求
此能力目前需要本地构建的 Rspack 原生 binding 和配套 JavaScript 包，包含 SSR 缓存失效与 `updateEntryExports` 支持，同时链接配套的 MF Runtime 和 Modern 代码。不能仅替换 Rspack 的 JavaScript 包，也不能据此认为已有发布版本支持此功能。不支持的 Rspack 构建会在配置阶段报错。
:::

## 开启能力

生产者和消费者保留已有 MF 配置，并在 `modern.config.ts` 中开启 `cacheUpdates`：

{/* prettier-ignore */}
```ts title="modern.config.ts"
import { appTools, defineConfig } from '@modern-js/app-tools'

export default defineConfig({
  plugins: [appTools()],
  server: { ssr: { mode: 'stream' } },
  moduleFederation: {
    ssr: { cacheUpdates: true },
  },
})
```

框架自动绑定服务生命周期内的更新管理器、SSR 资源和 Service 缓存，无需业务手动创建 `createSSRUpdateAdapter`。关闭能力时，不启用这条自动更新链路。

Service App 的纯 CSR 消费者也可以开启此能力，不要求额外打开页面 SSR。

## 生产环境主动更新

从 `@modern-js/runtime/mf` 导入 `shouldUpdateRemote` 和 `updateRemotes`。两者用于已启动的 Modern 服务端，浏览器代码不能通过它们直接替换服务端远端。

请在 Modern 编译的服务端代码中导入这些 API。发布控制器可以通过应用自行提供的受控入口触发调用。完整的 `mf` 入口还包含 React 和渲染集成，目前不支持未经打包的独立 Node 脚本直接导入。

下例由本应用请求上下文之外的后台发布控制逻辑执行。如果通过本应用的 HTTP 接口提交更新，该请求同样受到排空管理，应使用下节的 `defer: 'after-response'` 并返回 receipt。

{/* prettier-ignore */}
```ts
import {
  shouldUpdateRemote,
  updateRemotes,
  type RemoteUpdateTarget,
} from '@modern-js/runtime/mf'

const remote: RemoteUpdateTarget = {
  name: 'shop',
  entry: 'https://cdn.example.com/shop/mf-manifest.json',
}

if (await shouldUpdateRemote(remote, { revalidate: true })) {
  const result = await updateRemotes([remote], { revalidate: true })
  console.log(result.operationId, result.changed, result.generation)
}
```

`name` 是已经注册的远端名称或别名，`entry` 是 manifest 地址。生产者可以更新同一地址的 manifest，不要求每次修改消费者配置。框架比较部署元信息，包括构建标识、资源和 Service 地址，不使用 Runtime 可变的消费记录判断版本。

| API                                                   | 返回值                        | 行为                                           |
| ----------------------------------------------------- | ----------------------------- | ---------------------------------------------- |
| `shouldUpdateRemote(remote, options)`                 | `Promise<boolean>`            | 读取并比较候选版本，不清除当前缓存或发布新版本 |
| `updateRemotes(remotes, options)`                     | `Promise<RemoteUpdateResult>` | 排队执行，重新判断是否需要更新，成功后返回结果 |
| `updateRemotes(remotes, { defer: 'after-response' })` | `RemoteUpdateReceipt`         | 同步接收延后执行的任务，不返回完成 Promise     |

检查结果不会为后续更新保留一个已提交的版本。`updateRemotes` 自身会重新检查，因此也可以直接调用，并通过 `result.changed` 判断是否实际更新。相同候选可以合并，较晚提交的不同候选按管理器队列处理，业务不需要提供递增 revision。

可选参数的用途如下：

- `revalidate: true` 在需要请求 manifest 时使用 `no-store`，不会覆盖调用方已经提供的 `moduleInfo`。
- `signal` 用于取消候选读取等可中止工作。取消不保证恢复已经失效的应用状态。
- `application` 选择服务端 MF 应用名称。单应用进程可省略，多个应用共享进程且调用方不在应用请求上下文中时需要指定唯一名称。同名应用的请求内调用仍按请求归属选择，后台调用无法用相同名称区分它们，会拒绝执行。
- 远端描述中的 `moduleInfo` 可传入调用方已经读取的新 manifest 或 provider snapshot。它是候选部署数据，不是浏览器提供的可信上游配置。
- 远端描述中的 `client` 可携带配套的公开浏览器入口信息，成功更新后的 HTML 会携带该入口。对某个远端启用后，后续更新也必须提供配套的 `client`。首次调用之前已经发出的 HTML 不会被追溯修改，保留旧 HTML 的生产部署还需要初始版本映射及不可变的旧版本资源。

`RemoteUpdateResult` 包含 `operationId` 和 `changed`，实际执行更新时还可能包含 `generation`、`mode`、`entries` 和 `reasons`。生产环境不会自动轮询发布，也不会因服务端更新而主动刷新已经打开的浏览器。

更新选定候选模块信息后，Host 运行时和该应用的 Service ingress 在重建时使用同一份候选快照。用户的 `afterResolve` 插件需要保留这份快照选择的部署身份，仍然可以调整请求头等请求策略。固定模块信息不能保留被覆盖的产物字节，生产发布仍需要不可变的版本化资源。

开发构建为每次编译生成新的 `buildVersion`，manifest 和对应容器使用同一个值，不再增加独立的开发 revision。生产构建依次使用 `MF_BUILD_VERSION`、项目包版本和本地回退值。生产发布需要为不同部署分配可区分的版本。

浏览器和 Node manifest 合并时，`buildInfo.buildVersion` 保留浏览器版本，`ssrRemoteEntry.buildVersion` 保留 Node 版本。SSR 更新比较 Node 版本，单端更新不要求另一端重新编译。生产者运行时按生产者名称和所选构建版本定位。不要在构建完成后单独改写 manifest 的 `buildVersion`。

Modern 负责排空请求和发布应用版本。`@module-federation/node/runtimePlugin` 负责 MF 实例、容器、共享依赖和 host snapshot 的生命周期。MF bundler adapter 将清理请求交给 Rspack，模块依赖图、模块缓存、chunk 状态和过期加载判断由 Rspack 原生 runtime 管理。

如果目标生产者已被另一个应用加载，新 Host 会在执行渲染器前，复用该生产者已加载且包版本相同的 singleton 记录，保证保留的组件和 Host 使用相同的运行时依赖。非 singleton 依赖及其他包版本仍按 MF 的正常规则选择。如果选中的多个生产者已经使用不同的 singleton 实例，初始化会报错。

## 在 SSR 请求中延后执行

正在执行的 SSR 请求本身也是更新需要等待的工作。直接在它的 loader 或渲染流程中等待普通 `updateRemotes` 会让请求等待自身排空，因此框架会拒绝这种调用。

需要从请求内提交更新时，使用 `defer: 'after-response'`：

{/* prettier-ignore */}
```ts
import { updateRemotes } from '@modern-js/runtime/mf'

export async function loader() {
  const receipt = updateRemotes(
    [{ name: 'shop', entry: 'https://cdn.example.com/shop/mf-manifest.json' }],
    { defer: 'after-response' },
  )

  return { updateOperation: receipt.operationId }
}
```

此调用同步返回含 `operationId`、`revision` 和 `phase` 的 receipt。它表示任务已被接收，不表示新版本已生效，也不是可等待更新完成的 Promise。框架会在当前响应及其登记的生产者工作结束后，在请求之外执行更新。`revision` 仅用于诊断，不是调用方控制发布先后顺序的参数。

## 本地开发更新

启用能力后，Modern 复用 MF 开发 broker 建立独立的构建订阅。此通道不依赖类型生成，`dts: false` 仍可使用。订阅使用生产者名称和完整 manifest URL 区分生产者，端口及路径不同的同名应用不会相互覆盖。

生产者在 manifest、资源及 Node 应用就绪后发送通知。消费者在后台排空旧请求并更新 Node 缓存，成功后再通知浏览器重新验证路由数据。普通组件和 Bridge 的兼容 React Fast Refresh 更新可以保留页面状态。关闭 HMR、使用静态产物或无法保证热替换时，消费者在 Node 更新成功后整页刷新。

包含 Service expose 的生产者目前使用整页刷新，使浏览器 Service 描述与服务端 HTML 保持同一版本。这也保证卸载后再次挂载时不会继续发送旧版本请求，该路径会重新创建页面状态。

完成初次同步且连接健康时，SSR 请求不重复扫描 manifest。生产者只有本地 `build + serve`、尚未启动、连接中断或 broker 不支持订阅时，消费者在新 SSR 请求进入排空管理之前检查 manifest。一次并发请求合并为同批检查，独立远端并行读取，服务端支持时使用条件请求。此时手动刷新也会触发检查并更新 Node 缓存，读取失败会记录错误，后续请求仍可重试。

A→B→C 的依赖链会保留 A 的原始构建身份向下游传播，即使 B 本身未重新编译，C 仍能发现 A 的变化。请求兜底也会读取 manifest 中的嵌套依赖。嵌套依赖变化或删除时，更新释放旧依赖图并重建应用。

编译失败不会发布成功版本。消费者先启动导致初次 SSR 资源加载失败时，开发服务保留订阅与恢复入口，生产者就绪后可以恢复，无需重新编译消费者。订阅和检查共享服务生命周期，停止服务时一并清理。生产环境不启用这条自动检查或浏览器更新链路，仍使用上文的主动更新流程。

### 查看开发更新日志

生产者自身的新构建真正可消费后，终端输出 `[MF] shop ready`。消费者完成服务端更新并触发浏览器刷新后，输出 `[MF] shop updated`，同批远端合并为 `[MF] shop, cart updated`。仅依赖变化时不重复输出自身的 `ready`。没有实际变化时不输出成功消息，失败仍在消费者终端显示简短错误。这里的 `updated` 不表示浏览器已经完成渲染。

连接到支持诊断的 broker 后，终端提示一次 `[MF] logs: http://localhost:16322/__mf/logs`。使用终端显示的实际地址查看最近事件，人和 agent 使用同一个 HTTP 接口，无需猜测项目目录：

```sh
curl 'http://localhost:16322/__mf/logs?consumer=host&remote=shop&limit=100'
```

将示例地址替换为终端输出的地址，`consumer` 和 `remote` 替换为对应应用与远端名称。`remote` 也可以使用完整 manifest URL，`source` 可以按事件来源筛选。默认返回最近 100 条，`limit` 最大为 500。需要继续读取时，将响应的 `nextCursor` 作为下一次请求的 `after` 参数。

broker 记录连接、发布、通知及消费者实际应用成功或失败的结果，包含可用的构建标识、操作 ID、耗时与错误原因。订阅更新和 manifest 兜底检查都会回报结果。无变化检查与心跳不刷入更新日志，日志回传失败不会阻断更新。

默认保留 broker 内存中最近 2000 条、总计最多 2 MiB 的事件，不新增日志文件。历史被淘汰时响应的 `truncated` 为 `true`，broker 重启后历史丢失，旧游标请求的 `reset` 为 `true`。该接口只接受 broker 所在机器的本地请求，远程 broker 需要在对应机器上读取，不能把它的地址或文件路径当作当前项目的本地资源。旧 broker 不提供此接口时不会输出日志地址，开发更新仍按原方式运行。

需要文件记录时，在首次启动 broker 前设置 `FEDERATION_DEBUG=1`，日志沿用 broker 实际工作目录的 `.mf/typesGenerate.log`，MF 更新事件带有独立前缀。后启动的应用复用现有 broker，在这些应用中修改环境变量不会改变 broker 的日志设置。DTS worker 重启不会再删除该日志。broker 中的诊断不包含其他进程的全部 DTS 生成与下载日志。

## Service App 版本冲突

旧页面可能在生产者更新后发送携带旧 `buildVersion` 的 Service 请求。生产者在渲染前检查版本，不匹配时返回专用 typed HTTP 409，Modern 同源入口会保留该协议。普通鉴权或业务逻辑返回的 409 不属于此版本冲突。

`@module-federation/bridge-react/service` 和 `/service-node` 导出 `BridgeServiceVersionMismatchError`、`isBridgeServiceVersionMismatchError` 和 `BRIDGE_SERVICE_VERSION_MISMATCH`。错误携带 `expectedBuildVersion` 与 `actualBuildVersion`，用于区分请求版本和实际部署版本。

版本冲突保留其错误类型并交给现有错误 UI，不触发通用的 `?csr=1` 降级跳转，因为 CSR 仍会使用同一个 Service 协议。开发环境由构建订阅或请求前兜底完成更新，再整页刷新恢复。框架不会自动重放失败的 Service POST，也不会从该请求内发起需要等待自身的更新。生产环境的恢复交给业务策略决定。已经开始输出的流不会被改写成新的 409 响应。

## 更新与失败边界

更新先等待受影响的响应流和已登记生产者工作结束，再清除缓存并准备新资源。自动接入默认重建整个应用。底层适配器在显式配置静态消费约束、入口请求归属且所有权信息完整时，可以只重建受影响入口；动态消费或所有权不完整时仍使用整个应用重建。

普通 SSR 组件的静态导入及编译器可识别的 `import()` 会进入模块依赖图。清理包含远端模块及持有旧引用的宿主父模块，再重新创建 SSR 入口。运行时 `loadRemote()` 无法完整静态追踪使用方，因此使用整个应用重建。业务自行保存到应用资源之外的模块引用仍需要业务负责失效。

清理已开始后，如果新资源准备或发布失败，SSR 可能保持不可用，直到后续更新成功。框架不会把部分重建的应用当作完成版本放行，也不保证恢复已被清除的业务状态。业务全局副作用、第三方单例和旧版本浏览器资源的留存仍需要应用自身管理。

应用渲染与路由约束见 [Modern Bridge SSR](/guides/topic-detail/module-federation/bridge-ssr)，Service 部署与同源入口配置见 [Service App](/guides/topic-detail/module-federation/service-app)。
